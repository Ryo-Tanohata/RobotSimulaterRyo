# state.json が大きくなることをどうするか (計画。2026-11-06)

本物の村の `sim/society/data/state.json` が 50 MB をこえ、GitHub が注意を出している。
GitHub は 100 MB をこえるファイルを受けとらない。

この文書は計画だけ。コードも data も変えていない (data には書いていない。git にもさわっていない。LLM も使っていない)。
調べは、いまの state.json と git の履歴 (`git show <コミット>:sim/society/data/state.json` を流して読む) とコードを読むだけで行った。
前の計画 (app_data.json と season_person.jsonl) は `docs/society_phase/data_size_plan.md`。考え方 (日や印で切りかえて、前の歩のやり直しを 1 バイトも同じにする) はそれと同じ。

年の数え方: 年の集まりの日は 120 × 年 − 1 (例: 146年 = 17519 日目)。いまの速さは 1 年で 約 34 分。

## 0. みじかい答え

- いまの state.json (17519 日目、146年の年の集まり): **56.6 MB**。
- **その 42 % (23.7 MB) は、ほぼ 0 だけの「信頼」(trust) の表**。1 人ごとに、これまで村にいた全員 (1271 人。生きているのは 272 人) の名前と 0.0 が入っている。
  1614170 組のうち 0 でないのは **17 組だけ**。人の数 N の 2 乗で増える (app_data.json で外したものと同じ表。state.json にはまだ残っている)。
- 増え方: いまは 1 年 約 0.9 MB。そのうち 約 0.6 MB が trust (しかも N が増えるほど速くなる)、ほかは 約 0.3〜0.45 MB。
- **このままだと 100 MB に届くのは 175〜186年ごろ (あと 約 30〜40 年 = 村を回して 約 17〜23 時間)**。90 MB は 168〜178年ごろ。
- **おすすめ: 案 A「state.json の trust から 0 を外す (印で切りかえる)」**。56.6 MB → 約 32.9 MB。
  そのあとは 1 年 約 0.3〜0.45 MB しか増えず、50 MB の注意は 184〜203年ごろまで出ない。100 MB は 290年より後。
  お題の文は 1 文字も変わらない (0 の人も「+0.0」と前と同じに出す)。前の歩のやり直しも 1 バイトも同じのまま。

### 2.1 見込み

全体 ≒ 14.7 × N² + (ほか 32.9 MB + r × 年)。N が 1 年 dN 人ずつ増えるとして計算した。

| dN (1 年に増える人) | r (ほかの増え方) | 90 MB | 100 MB | 案 A のあと 50 MB | 案 A のあと 100 MB |
|---|---|---|---|---|---|
| 17 | 0.30 MB | 178年 | 186年 | 203年 | 340年より後 |
| 17 | 0.45 MB | 174年 | 182年 | 184年 | 296年 |
| 21 | 0.45 MB | 171年 | 177年 | 184年 | 296年 |
| 25 | 0.45 MB | 168年 | 173年 | 184年 | 296年 |

- **何もしないと、あと 約 27〜40 年 (村を回して 約 15〜23 時間) で 100 MB**。そのずっと前から 50 MB の注意は出つづける。
- 季節によって ±1〜2 MB ゆれるので、上の年より 1〜2 年早く届くこともある。

## 3. trust をだれが書いて、だれが読むか

- 作る:
  - `world.py` 145 行 (はじめの村を作るときだけ): `{n: 0.0 for n in names if n != name}`。
  - `era2.py` 162 行 `_new_person`: 新しい人に `{n: 0.0 for n in names}` (それまでの全員。亡くなった人・出た人も)。
  - `era2.py` 169 行: それまでの全員 (亡くなった人も) に、新しい人の名前で 0.0 を足す。**ここで N × N になる。**
- 変える: `world.py` 748 行 (食べ物を分けたとき、+0.15)。`b["trust"].get(a["name"], 0)` なので、名前がなくても動く。
  ほかに trust を変えるところはない (`era2.py` の `o["trust"]` は、よその集落 (others) の信頼で、別のもの)。
- 読む:
  - `characters.py` 37 行 `_me` (**お題の「仲間への信頼 (-1〜+1)」の行**): trust の順に、生きている大人 (子どもでない) の名前を `+0.0` の形で並べる。
    0 の人も並べるので、0 を外すと、そのままではお題の文が変わる。
    `_me` は `characters` のお題・`era2.py` 2757・3664 行・`g7.py` 1943 行 (季節・気持ちのお題) から呼ばれる。
  - `resume.py` 138 行 (履歴書。app_data.json 用): `names` にある名前だけ。そのあと step.py の export が (APP_SLIM_FROM のあと) 0 でないものだけにする。
  - `tools/*.py`・`app/`・`video/`・`standalone.py` は state の trust を読まない (`tools/test_g7.py` の T_AppSlim は app_data の trust だけ)。
- 調べたこと: いまの state で、どの人の trust の名前の順も「people の順から自分を除いたもの」とぴったり同じ (1271 人みな)。名前の重なりもない。
  だから、0 を外しても、**people の順に生きている大人をたどり、`trust.get(名前, 0.0)` を出せば、お題の行は前と 1 文字も同じ**になる。
- 古いもの (亡くなった人・出た人の名前の 0) は、世界の仕組みではどこも使っていない。0 でない 17 組だけが意味のある記録。

ほかの大きいものについて:

- `events` の「しまった年の写し」(8.7 MB): `archive.py` の KEEP_TYPES (話す・加わる・育つ・まとめ役・よその便り・きっかけ)。
  知識と掟の札・家族を決める・来た日・種から育った木・まとめ役なしの道が、しまった年までさかのぼって読む (archive.py の頭の説明)。年のファイル (`archive/events_YYYY.jsonl`) にも同じものが入っている。増え方は 1 年 約 30 KB で小さい。
- `events` の今の年と前の 2 年 (10.8 MB): `archive.KEEP_YEARS = 2`。しまう仕組みはもう動いている。生きている人が増えるぶんだけ増える。
- 亡くなった人の `heard` (2.4 MB)・`knowledge` (1.1 MB): 1 人 30 件までなので、亡くなる人の数だけ増える (1 年 約 50 KB)。
  `heard` は `characters.py` 150 行 (お題。生きている人だけ) が読む。`knowledge` は `resume.py` 129 行 (履歴書の「いま知っている数」) などが読む。

## 4. 案

### 案 A: state.json の trust から 0 を外す (印で切りかえる) 【おすすめ】

- 中身: 印 `state["trust_sparse"] = {"day": D, "why": "…"}` がある state では、trust に 0 でないものだけを持つ (ない名前 = 0.0)。
- コードの変更 (小さい):
  - `step.py`: 新しいコマンド `slim_trust --why "<わけ>"`。年の集まりで止まっているときだけ (slim_app と同じ止まりの確かめ)、
    印を書き、すべての人の trust を `{k: v for k, v in trust.items() if v}` にして (people の順のまま) state.json を書く。日・お題・ほかの世界は変えない。
    `TRUST_SPARSE_FROM = D` を足し、その日のほかは断る (APP_SLIM_FROM と同じに、どこで切りかえたかがコードに残る)。
  - `era2.py` `_new_person` (162・169 行): 印があれば、新しい人の trust は `{}`、ほかの人に 0.0 を足さない。印がなければ前のまま。
  - `characters.py` `_me` (37 行): `"、".join(f"{q['name']} {p['trust'].get(q['name'], 0.0):+.1f}" for q in state["people"] if q is not p and q["alive"] and not q.get("child"))`。
    前の形 (印なし) の state でも、前と 1 文字も同じ文になる (順が people の順と同じことを 3. で確かめた)。ついでに、いまは 1 人ごとに N × N の探しかたなのが N で済む。
  - `world.py` 748 行・`resume.py` 138 行は変えなくてよい (`.get(…, 0)`・0 でないものは同じ順のまま残る)。
- 1 バイトも同じでなければならないもの:
  - 印がない state (D より前の歩、data_E3_*・data_E4_* の実験の村) は、前と同じに動く。だから D より前の歩のやり直し (`tools/exp3_replay.py`) は同じ。
  - D の state を作った歩のコミットは、前の形の state.json のまま (slim_trust は別のコミットで入れる)。そのやり直しも同じ。
  - D からあとの歩は、新しいコードで作ったものが本物なので、やり直しても同じ。
  - お題: D の日のお題 (prompts/dayD) は、slim_trust の前後で sha256 が同じになるはず (確かめる)。
  - app_data.json: 履歴書の trust は「0 でないもの」だけで、順も同じなので、slim_trust の前後で同じになるはず (確かめる)。
- 大きさ: 23.70 MB → 約 0.02 MB (`"trust":{}` が 1271 人ぶんと 0 でない 17 組)。**state.json は 56.6 MB → 約 32.9 MB**。
  そのあとの増え方は 1 年 約 0.3〜0.45 MB (trust の増え方がなくなる)。50 MB は 184〜203年ごろ、100 MB は 290年より後 (2.1 の表)。
- 危うさ: 小さい。気をつけること:
  - これから trust を読むコードを足すときは、いつも `.get(名前, 0.0)` で読む (HANDOFF.md に書く)。
  - D より後の日に 0 でない組の順は、0 でなくなった順になる (前は people の順)。お題は people の順に出すので変わらない。履歴書の「信頼している人」は大きい順に並べかえて見せるので見え方も同じ。

### 案 B: 亡くなった人・出た人の heard (と knowledge) を年のファイルに移す

- 中身: 亡くなった人の `heard` (2.4 MB) を `archive/people_YYYY.jsonl` (亡くなった年) に移し、state からは消す。
  `knowledge` (1.1 MB) は履歴書が数を読むので、移すなら履歴書の作り方も直す。
- コードの変更: archive.py (しまうもの・戻すもの)・step.py (しまうとき)・resume.py (knowledge の数)・`full()` で戻す。日の切りかえ (印) が要る。
- 大きさ: 今 2.4〜3.5 MB 減る。増え方は 1 年 約 50 KB 減るだけ。
- 危うさ: 中くらい (亡くなった人の中身を読むところを全部調べる要がある)。**得るものが小さいので、いまはしない**。案 A のあと、もし要れば。

### 案 C: しまった年の出来事の写し (8.7 MB) を軽くする

- 中身: KEEP_TYPES の写しから、世界が読まない鍵 (たとえば話すの text) を外す。または KEEP_YEARS を 2 → 1 にして今の年の出来事を 約 3.5 MB 減らす。
- 問題: 知識の札・家族・種から育った木・年の名前のお題などが、どの鍵をどこまで前まで読むかを、もう一度全部調べる要がある。お題が変わりやすい。
  増え方も 1 年 約 30 KB と小さい。
- 危うさ: 中くらい〜大きい。**しない** (案 A で足りる)。

## 5. 入れる手順 (案 A。本物の村が年の集まりで止まっているとき)

止めるのは「年の集まりのお題が出て、まだだれも答えていない」ところ (例: 147年の年の集まり = 17639 日目)。この日を D とする。

1. 止まっていることを確かめる: `python3.13 sim/society/step.py who` → `DAY D season False`・`HOLD none`・`MEET 年`。季節を進めるワークフローが動いていない。`git status` で data に書きかけがない。
2. ブランチでコードを直す (4. の案 A)。`TRUST_SPARSE_FROM = D`。
3. 試し (どれも data の写しで。本物の data には書かない):
   - `tools/test_g7.py` に T_TrustSparse を足す:
     前の形の state で、新しい `_me` と前の式の文が、生きている大人みなで同じ。
     slim_trust の前と後で、すべての人の `_me` の文が同じ。0 でない組は残る。印のある state で `_new_person` が 0 を足さない。印のない state では前と同じ。
     D のほかの日・答えがある日は slim_trust が断る。
   - `tools/exp3_replay.py --commits <最後の 2〜3 の歩のコミット>` → state・app_data・archive・次のお題がみな「同じ」。
   - 写しで slim_trust → prompts/dayD のお題を作り直して sha256 が前と同じ・app_data.json が前と同じ。
   - 写しで slim_trust のあと 1 季節進めて (LLM のかわりに前の答えで)、止まらず動くことを見る。`test_archive.py`・`test_hints.py` を回す。
4. 本物の data で `python3.13 sim/society/step.py slim_trust --why "state.json が 50 MB をこえた (docs/society_phase/state_size_plan.md の案 A)"`。
   state.json が 約 33 MB になる・prompts/dayD の sha256 が同じ・app_data.json と records/ が同じ、を見る。
5. 本人が見てコミット (コード・試し・HANDOFF.md・この文書・state.json)。年の集まりに答えて村を続ける。
   最初の季節のコミットで、state.json が 約 33 MB のままであることと、その歩を `exp3_replay.py` でやり直して「同じ」を見る。
6. もどすとき: コードの読み方 (`.get(…, 0.0)`) は残す (印のある state が履歴に残るので)。

## 6. あとで考えること (いまはしない)

- state.json の「今の年の出来事」は、生きている人が増えるほど増える。生きている人が 500 人をこえるころにもう一度はかる。
- リポジトリ全体 (pack) の増え方は、state.json の差 (季節ごとに書きかわるところ) で決まる。trust はほとんど書きかわらないので、案 A で pack の増え方はあまり変わらない。
- 履歴に残った 50 MB 台の版は消さない (100 MB の上限はファイルごと・プッシュのとき)。
